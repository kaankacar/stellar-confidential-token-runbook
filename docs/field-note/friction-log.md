# Friction log: Confidential Tokens on Stellar (OpenZeppelin, stellar-confidential 0.8.0)

What we hit while building Who Ate Gerald? on the developer preview (Bri, July to September 2026) and while running the six steps on the stable release (Kaan, 23 November 2026, five weeks after the 20 October 2026 release of `stellar-confidential` 0.8.0). Only the problems that change a developer's experience and that OpenZeppelin can act on. One row per problem: what we were doing, what went wrong, the fix or workaround, and whether it is fixed (on OpenZeppelin's side), open (still there, our workaround is in the row), or by design (not a bug, but worth writing down). The long list, our own mistakes and tooling included, is in [friction-log-full.md](friction-log-full.md). Repo: https://github.com/kaankacar/stellar-confidential-token-runbook. Game: https://github.com/briwylde08/who-ate-gerald.

| # | While doing | What went wrong | Fix or workaround | Status |
|---|---|---|---|---|
| O1 | Installing the client SDK | There is no npm package from OpenZeppelin. The SDK is a git dependency from a personal repo (`brozorec/stellar-confidential-token-sdk`), and `npm install stellar-confidential-token-sdk` installs an unrelated project (0.1.9 by another author). The README's pnpm advice (`pnpm.onlyBuiltDependencies` in package.json) works on pnpm 10 and is ignored by pnpm 11. | Git dependency pinned by commit (`#aad1706`); on pnpm 11, `allowBuilds` in `pnpm-workspace.yaml` with the tarball URL as the key. Ask: publish under an `@openzeppelin` scope or reserve the npm name, and document the pnpm 11 form. | open |
| O2 | Copying the end-to-end example to register an account | `scripts/e2e.ts` derives the confidential keys from `randomScalar()`. Registration is single-use per account, so a developer who copies it and loses the process has an account that can never be registered again. The SDK ships the recoverable derivation (`skSigningPayload`, `deriveSk`) and the example does not use it. | Derive from a SEP-53 signature by the account key, verify it, derive twice, compare; `scripts/lib/keys.ts` in the runbook. Ask: make the example use the recoverable path and say why in one comment. | open |
| O3 | Syncing a state engine on the public deployment | The example starts every `StateEngine` at `deployedAtLedger`. A week after deployment the testnet RPC refuses it: "startLedger must be within the ledger range". The SDK rethrows the raw JSON-RPC object, so the message a developer sees is `[object Object]`. | Start each engine at the ledger the account registered in; stringify non-Error throws. The game's vendored SDK clamps `startLedger` to `getHealth().oldestLedger` locally. Ask: clamp in `fetchEvents` and wrap RPC errors in an `Error`. | open |
| O4 | Proving for the first time against a deployment | Nothing checks that the verification keys registered on chain are the ones the SDK bundles. The README declares the gap. A mismatch shows up only as an on-chain rejection after a proof was built. | `pnpm recon` simulates `get_verification_key` for the six circuit types and compares SHA-256 with `circuits/manifest.json` (6 of 6 matched on both deployments). Ask: ship the check, for example in `versionMatrix(token)`, and run it before the first proof. | open |
| O5 | Registering the first account on the month-old public deployment | The call cost 2.77 XLM; the second account one ledger later cost 0.015 XLM. The first call restored 8 archived ledger entries (verification keys, auditor key, token instance) whose TTL had passed. Nothing in the SDK or the README mentions TTL or restoration, and a vanilla token has no admin to extend anything. | Expect it, or extend the TTLs after deployment. On a fresh deployment the same registration cost 0.021 XLM. Ask: a README note on TTL and `extend-ttl` for the verifier and auditor entries. | open |
| O6 | Reading the docs page before starting | https://docs.openzeppelin.com/stellar-contracts/tokens/confidential/confidential says the demo runs on a pre-0.8.0 deployment. The demo repo and the live site moved to 0.8.0 on 24 and 25 October. | Trust the demo README, not the docs page. Ask: update the page. | open |
| O7 | Explaining the two balances | The blog and the game say "pending"; the code, the events and the docs say "receiving". Both describe the same balance, and a reader coming from the blog searches the code for a word that is not there. | One sentence in the note. Ask: pick one name in the docs and mention the other once. | open |
| O8 | Choosing where proofs run (Bri) | Proof generation needs memory. It runs in a browser or in Node (one prover took 303 MB RSS in Node 24), and it is a non-starter in 128 MB serverless workers. The README says "construct provers once and reuse them" but gives no memory floor. | Proofs in the browser for players, merges signed by the server (no proof), withdrawals by a script outside the main loop. Ask: document the memory floor per prover and the browser, Node and worker options in one place. | open |
| O9 | Supporting passkey accounts (Bri) | Registration binds the key hierarchy to one address. WebAuthn assertions are not stable for key derivation (random challenges; the PRF extension's support is spotty), and a passkey wallet on Stellar is usually a new contract account, so a user who moves to one is a new participant whose balance does not follow without a public withdrawal and deposit. | Ed25519 wallets only for now (SEP-53 signer roots). Ask: a documented derivation path for contract accounts. | open |
| O10 | Reading the demo README and the package README | The demo README says the verifier and circuits are unaudited, while the v0.8.0 release notes and the audit report cover them. The caveat that matters most, the verifier accepting only non-zero-knowledge proofs, sits in the package README and not on the docs page. | Read the release notes and the audit PDF. Ask: align the demo README with the audit, and surface the non-ZK caveat on the docs page. | open |
